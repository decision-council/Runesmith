# Acceptance checks that free models can get right

Status: **design, not built.** Reviewed 2026-09-27 by an adversary, a feasibility reviewer and a generality reviewer (Sonnet), then synthesised. The evidence and the paced model experiment are in `D:/oob/JOURNEY_LOG.md` (Phase B) and `D:/oob/experiments/checkers/FINDINGS.md`.

## Why
In journey R1 Phase B a free fast model (Gemini 3.1 Flash Lite) built milestones m4–m6 correctly on the first attempt, but wrote weak acceptance checks across four rounds. The weaknesses: hidden exact text, vacuous checks, wrong-reason failures, sentence/code contradictions, weak substring assertions, no way to simulate failures, and a missing sentence.
- G1.1–G1.3 (assumptions, trial run, one revision, unstated-text detection) and the Checker role made the flaws visible and let a stronger model take over.
- This design aims to let weaker free models produce trustworthy checks themselves. The idea is to chunk the task so the model only does what it is good at: understanding behaviour and giving examples. Runesmith does what must be exact: code, fault simulation, and strength testing.

## Decision rule
Build this only if the paced experiment shows that free models (Gemini Flash tier, gpt-oss-120b) do **not** reach sound checks on the current pipeline, sound meaning they fail before the milestone, pass on two different correct builds, and catch deliberately broken builds.
- If a free model scores sound, it becomes the recommended free Checker, and this design is hardening for after the out-of-box release. That order is also what [ADAPTIVE_GRANULARITY.md](ADAPTIVE_GRANULARITY.md) recommends.

## Refined design (synthesis)

Short answer: yes, chunking the checks is buildable and worth doing, but only if six mechanical gates are wired in explicitly rather than assumed. Below is the six-step design from the reviewers' brief, kept in its original shape, with each reviewer's must-fixes folded in as an explicit safeguard at the step where it belongs, and marked model vs Runesmith at every step.

0. Scope (Runesmith decides, no model call). v1 covers CLI/subprocess projects (any target language, proven live by m4-m6) and Python library import/call. Web/HTTP services and GUIs are an explicit non-goal for v1 (they would need a network exception that collides with acceptance_proposals.NETWORK_MODULES, or a browser-automation layer that does not exist in building.py's headless unittest runner). This single scoping decision retires two of the adversary/generality musts (the network fault menu item, and GUI/service coverage) without weakening anything the journey actually proved.

1. Clause split — Runesmith splits done_when deterministically (sentence/semicolon/"and" segmentation of the field already fetched in _milestone(), acceptance_proposals.py:81-85), no model call. Runesmith then runs a required_texts-style coverage diff in the reverse direction: every literal/number/named entity in the original done_when text must appear in the union of clauses; anything left over is shown to the owner as an uncovered clause instead of silently dropped. Model-driven adaptive splitting is deferred to a later slice, once templates are proven at today's granularity (feasibility's recommendation) — a mis-split clause is prose, not code, so it has none of required_texts' AST safeguards until this coverage diff exists.

2. Examples, not code — the model returns, per clause, {clause, setup, action, expected (matcher + params), why_fails_today, fault (only from Runesmith's closed menu), sentence} as data, never code. The owner reviews a table, not a diff.

3. Runesmith re-derives the expected value — for every mechanically-checkable outcome (count, order, presence/absence — exactly the matcher types the templates support), Runesmith recomputes the expected value from the stated setup with its own small trusted calculator and rejects a mismatch before the example reaches the owner or spends an ordinary_allowance attempt. This is new versus the original brief: nothing in steps 4-6 alone verifies the model's example data is internally correct, only that the resulting check behaves consistently.

4. Trusted templates render examples into unittest code (Runesmith only, no model call): run-a-command + tolerant matchers (line-with-field-has-number, ordered sequence, word-boundary-safe contains/absent, exit status), no-Traceback + file-unchanged/exists, README-example extraction, and the fault menu implemented as ONE open()/io.open-patching template with parameters — interrupted write, damaged file, missing file, and read-only folder folded into the same mechanism (raises PermissionError unconditionally for paths under the target folder) instead of relying on real OS permissions, which do not reliably block writes on the Windows platform this runs on. The template also renders the owner-facing sentence from the same {field} values the matcher checks, so hidden-exact-text and sentence/code contradiction become structurally impossible rather than merely detected. required_texts() still runs over the rendered code as cheap defense-in-depth against a template bug that leaks an extra literal, and is extended to flag any literal present in an example/sentence but absent from the milestone's own done_when text (an explicit "assumption," same shape as today's G1.1 assumes list). An AST scan for non-determinism (datetime.now(), unseeded random, sleep, locale formatting) runs alongside it. Before any template is marked "trusted" it ships with its own meta-test suite covering every documented weak-assertion case (assertIn('2','2026'), "any nonempty stderr is a clear error," etc.), rerun on every template change — this is the one place a codified regression test replaces what today only a hand-written checker did correctly.

5. Fails today AND passes on a reference — this is the fix for the exact bug that shipped (m6's README check, JOURNEY_LOG.md:137-140,147-149). Runesmith dry-runs the rendered check twice before offering it to the owner or auto-approving anything: once against today's project (existing dry_run(), extended to carry the RUNNER's already-computed failure_details/trace_tail through instead of discarding it, building.py:66-70), and once against a throwaway reference implementation (owner-supplied when available, else a second small-model "obviously correct" stub). "Fails today" alone is necessary, never sufficient — the design's whole premise came from a check that failed today for a plausible reason and then broke a genuinely correct build. Runesmith compares the actual failure's trace_tail against the example's stated why_fails_today and flags a mismatch as a wrong-reason failure, routing to the existing one-revision flow. For fault-menu examples, the fault template records a sentinel when its own injected exception is what propagated — deterministic, and independent of the target project's exact wording.

6. Mutation testing gates apply, it does not audit after the fact — hooked inside verify_draft(), immediately after oracle = _run_checks(...) succeeds (building.py ~281) and strictly before record()/return (~288-292), so it runs before _apply_if_current can ever fire in that same call (building.py:690-698,726-765). Mutates frozen_files' bytes in Runesmith's own process (an AST mutator, same spirit as the existing _literals/required_texts/encode_like helpers) — never inside the subprocess — and runs each mutant through the unchanged _run_checks() on its own fresh clean stage, exactly like today's acceptance-stage pattern (building.py:277-278), so both "runners never import runesmith" and "checks run on a clean copy" hold by construction. Mutant count is small and capped (comparable to the existing 8-check cap) with digest-based caching so nothing re-runs when nothing changed (reusing _unchanged_verdict(), building.py:305-326). Decision made explicit, where the original brief left it open: a surviving mutant on an approved check BLOCKS auto-apply (a small persisted mutation-survival record checked in _apply_if_current's `valid` computation) rather than being advisory. An advisory-only warning that fires after the apply already happened reproduces the exact failure mode chunking exists to prevent; relax to advisory only if measurement (see experiment) shows the gate's latency cost is not worth it.

7. Best-of-N is a noise filter, never a safety mechanism — several cheap per-clause calls are compared by structured-field equality (command, matcher type, literal values, normalized) not natural-language similarity or an LLM judge. Steps 3, 5 and 6 run regardless of vote agreement, because the documented failures (vacuous, wrong-reason, weak-substring) were the same free model repeating the same category of mistake across m4, m5 and two revision rounds — correlated, not independent, so agreement is expected to converge on the same flaw as often as on the truth. Owner escalation on disagreement is not the unattended default (Phase B's premise is an owner away for days): the default prefers whichever example survives steps 3/5/6, or the smaller-scope one if several survive; the owner is only pulled in when the mechanical gates cannot resolve it themselves.

8. Call budget — total calls per milestone are capped up front (clauses x votes, mirroring SCHEMA's existing maxItems:8), a single clause-call failure/timeout is treated like today's PlannerUnavailable rather than retried silently across all clauses, and the pipeline degrades gracefully under capacity pressure (fewer votes, then one call per clause, then fall back to today's whole-milestone propose()) instead of stalling — this exact journey hit "nvidia capacity reached" and a 211s Kimi timeout at far lower call volume (JOURNEY_LOG.md:90-91,130).

9. Testability routing — Runesmith classifies whether a clause's expected outcome maps to a supported matcher; a clause that cannot (a subjective/architectural claim like "the message is friendly") is routed to owner sign-off instead of being forced into a template, avoiding a vacuous-by-construction check.

10. Owner UI is additive — an example table (clause, setup, action, expected/matcher, why-fails-today, fault, sentence) reusing goals.js's existing provenance-agnostic accBlock rendering and server.py's milestone/proposal-id-only approve/discard endpoints; no new backend surface.

Underneath all of this, today's free-form propose() stays as the fallback with every current safeguard intact (validate(), required_texts, dry_run trial, one revision, Checker role, replace-with-reason) — used for clauses routed away by step 9 and for out-of-scope target types from step 0. Nothing in this design needs a new Thinking-power role: chunking and voting are just router.call('acceptance', ..., key=...) repeated with different keys, exactly the pattern _revise_once already uses.

## Example schema

Per-clause example the model returns as data (no code at this stage):

{
  "clause": "<verbatim/lightly-normalized segment of the milestone's done_when text this example covers>",
  "setup": [ {"action": "<a step named from the milestone's declared CLI command or public function, e.g. add>", "args": {...}}, ... ],
  "action": {"kind": "command" or "call", "command": [...] or "function": "<name>", "args": {...}},
  "expected": {"matcher": "line_with_field_has_number | ordered_sequence | contains | absent | exit_status | no_traceback | file_unchanged | file_exists | readme_example", "params": {...}},
  "why_fails_today": "<short, checkable claim about today's failure, e.g. unknown command 'months'>",
  "fault": null, or {"kind": "interrupted_write | damaged_file | missing_file | readonly_folder", "target": "<path pattern under the setup's temp folder>"},
  "sentence": "<plain English; must be renderable from the same field values expected.params uses, so sentence and matcher cannot drift apart>"
}

Filled-in Reading Log example (milestone m4, the "months" clause):

{
  "clause": "python -m readinglog months prints, for every month with finished books, that month and how many books finished it",
  "setup": [
    {"action": "add", "args": {"title": "Book 2025-01-05", "author": "Someone", "finished": "2025-01-05"}},
    {"action": "add", "args": {"title": "Book 2025-01-20", "author": "Someone", "finished": "2025-01-20"}},
    {"action": "add", "args": {"title": "Book 2025-03-02", "author": "Someone", "finished": "2025-03-02"}}
  ],
  "action": {"kind": "command", "command": ["months"], "args": {}},
  "expected": {"matcher": "line_with_field_has_number", "params": {"field_pattern": "YYYY-MM", "field_value": "2025-01", "number": 2}},
  "why_fails_today": "unknown command 'months'",
  "fault": null,
  "sentence": "Running months after two January books and one March book shows a line for 2025-01 with the number 2."
}

Runesmith's own recomputation (design step 3, before this example is even shown to the owner): count of setup rows whose finished date starts with 2025-01 is 2, which matches expected.params.number = 2 — accepted. A model that miscounted here (claimed 3, say) would be rejected before the owner ever sees the table, independent of whether the rendered check itself later passes its dry-run and mutation gates.

## First templates

- run-a-command + tolerant line matcher: field-as-regex (e.g. YYYY-MM) plus last-number-on-the-line, adapted directly from m4.py's MONTH regex approach
- ordered-sequence matcher: a list of field values must appear in the stated order, adapted from m4.py's oldest-first test
- word-boundary-safe contains/absent matcher: closes the assertIn('2','2026') class of bug the free model actually shipped, by construction rather than convention
- exit-status + no-Traceback matcher, adapted from m5.py's damaged-file test
- file-unchanged / file-exists matcher via byte comparison, adapted from m5.py's damaged-file byte check
- README-example extraction-and-run matcher, adapted from m6.py, but first learning the target CLI's real argument grammar from its own --help output before running an extracted example, since the bug that actually shipped (--file placed after the subcommand) was a grammar mismatch a fixed hard-coded example could not catch
- fault: interrupted write, one open()/io.open-patching template parameterized by target folder, adapted from m5.py's HalfWriter
- fault: damaged file, corrupt-bytes fixture applied before the run, adapted from m5.py
- fault: missing file, delete before the run
- fault: read-only folder, implemented as the SAME open()-patching template as the three faults above (raises PermissionError unconditionally under the target folder) rather than real OS permissions, so it actually faults on the Windows platform this runs on
- explicitly excluded from v1: any network/slow-connection fault or HTTP-service template, since it would collide with acceptance_proposals.NETWORK_MODULES and needs its own scope decision before being offered as a model-selectable menu item

## Smallest first slice

Smallest buildable slice (feasibility's estimate, with step 5's reference-implementation check pulled forward rather than deferred, since it is the one gap that actually shipped a live bug): acceptance_templates.py (~300-400 lines: templates 1-5 and 7-9 from the list above, adapting m4/m5/m6 directly; defer README-grammar-learning and the unified read-only-folder variant to the next slice), acceptance_examples.py (~150-250 lines: the example schema above, validate_examples(), and propose_examples() rendering ONE example per milestone — today's granularity, no clause split, no voting yet — into the existing {checks, assumes, code} shape, PLUS the reference-implementation dry-run from step 5 before persisting a proposal), a small refactor pulling propose()'s persistence tail (validate -> dry_run -> findings/revise -> persist -> ledger, acceptance_proposals.py:250-263) into a helper both the free-form and example paths call, worker.py/server.py wiring mirroring the existing propose_acceptance job (~15-25 lines), and a goals.js additive table-rendering branch (~80-150 lines). Total order of magnitude ~600-900 lines, comparable to one G1.x release already shipped in a single evening per the journey log.

How to measure it on the Reading Log, free-only vs tonight: "free-only" means running propose_examples() through the same temporary Milliner gate and free route Phase B used (Gemini 3.1 Flash Lite via NVIDIA), since that is the honest test of whether the new pipeline fixes a free/weak model's behavior rather than a stronger model's. The full measurement is the protocol in the experiment field below (multiple cold runs, ablated gates, m4/m5/m6). What is realistically achievable "tonight," in one evening at Phase B's own pace, is a single smoke pass: run propose_examples() once each for m4, m5 and m6 against the live Reading Log project, and check by hand whether the 7 documented flaws recur — this is a go/no-go signal, not the reliability number; it tells the owner whether the slice is worth the full experiment, not whether it is safe to leave unattended. This task is read-only and made no code changes and ran no checks or the Studio, so neither the smoke pass nor the full experiment has been executed here — both are the concrete plan to hand to whoever builds the slice.

## Open risks

- Gating auto-apply on mutation survival (design step 6) adds a real subprocess cost (CHECK_TIMEOUT_S=120s per mutant, building.py:28) on every apply round; the decision to gate rather than warn needs to be checked against actual wall-clock cost once measured, not assumed correct at design time.
- The reference-implementation fallback in step 5, when the owner has not supplied one, is a second small-model 'obviously correct' stub — itself a weak-model artifact that could share the same category of mistake as the check it is meant to validate; no reviewer proposed a mechanical safeguard for this specific case beyond preferring an owner-supplied reference when available.
- README-grammar-learning (template 6, reading --help before running an extracted example) is new engineering beyond a straight port of m6.py; its scope and failure modes are unspecified and it is deferred past the first slice.
- Web/HTTP services and GUI targets remain out of v1 scope with no committed timeline for a loopback-only network carve-out; a milestone that genuinely needs one will fall back to today's free-form path with no template support at all.
- Deterministic clause-splitting (sentence/semicolon/'and' segmentation) may mis-segment a done_when with more complex structure than Reading Log's; the coverage diff (step 1) catches missed or leftover text but not a clause that is split in a way that quietly changes its meaning while still covering the same literals.
- Gating _apply_if_current on a persisted mutation-survival flag is a change to an existing, carefully-invariant-checked function (building.py:726-765); it needs its own focused review before shipping, independent of the rest of this design.
- Sol's own ADAPTIVE_GRANULARITY.md (D:\Runesmith\docs\design\ADAPTIVE_GRANULARITY.md) recommends building granularity work after the out-of-box release gate, to prove the first-user journey on today's machinery first; this chunked-checks design inherits the same sequencing question and was not resequenced by this synthesis.

## Honest experiment

Metric and design for measuring free-only acceptance-check reliability honestly, once the first slice exists: pick the milestones whose reference behavior and documented flaw history are already known (Reading Log m4, m5, m6 — the exact recipe in JOURNEY_LOG.md:87-171). Run propose_examples() end-to-end N=10 times per milestone (30 trials total), each a cold run with no memory of a prior attempt, using only the free route through the same temporary gate Phase B used (Gemini 3.1 Flash Lite via NVIDIA) — free-only, matching the constraint that actually produced the documented failures, not a stronger model that might mask them.

Run it as an ablation, not a single pass/fail count: for each trial, record which of the 7 documented flaw categories (hidden exact text, vacuous check, wrong-reason failure, sentence/code contradiction, weak substring match, inability to simulate a failure, a test without a sentence) would have reached owner-approval-eligible state with steps 3, 5 and 6 (recompute-expected, reference-pass, mutation-gate) disabled, versus with them enabled. This measures what the new gates actually catch, not just whether the pipeline eventually converges to something plausible.

Success criterion: with all gates enabled, zero of the 7 flaw categories reach an approval-eligible state across all 30 trials, and the owner needs zero rescues for the unattended building step itself — matching Phase B's own achieved bar (0 rescues, 3 owner actions total: approve checks, replace one faulty check, flip the schedule; JOURNEY_LOG.md:158-171). A single surviving flaw in the gates-enabled arm is a genuine finding given that sample size, not noise.

Honesty guard: report call count and wall-clock latency per milestone under the new pipeline alongside the accuracy numbers, and compare against today's propose() (2 calls, 5-15s good case) and against the capacity/timeout conditions this exact journey already hit (F12 pre-admission refusal with no fallthrough, JOURNEY_LOG.md:90-91; a 211s-per-call, 10.5-minute total Kimi K3 timeout, JOURNEY_LOG.md:129-132) — reporting only accuracy while hiding call-volume and latency cost would misrepresent whether the design is actually usable unattended. This experiment has not been run as part of this task: it is read-only, made no code changes, and ran no checks or the Studio; this is the protocol to execute once the first slice is built.

## Reviewer verdicts

### adversary

The six-step design correctly generalizes the granularity idea already validated for builds (D:\Runesmith\docs\design\ADAPTIVE_GRANULARITY.md) to check-writing, and its core move — templates plus owner-visible structured examples plus a trial plus mutation testing plus a closed fault menu — is the right shape for most of the seven failure modes actually observed live in Phase B (hidden exact text, vacuous checks, sentence/code contradiction, weak substring assertions, inability to simulate failure). But the design as written has real, specific holes, and at least one of them maps exactly onto a bug that already shipped in this journey: step 4 ("fails for the stated reason") only tests the fail-today direction, never whether the check would actually PASS once the project is genuinely built correctly — which is precisely how m6's check survived proposal, trial, and Checker review, then broke the 21:07:57 chained apply, because nobody had run it against a correct README until Claude did so by hand outside the design's mechanized steps (JOURNEY_LOG.md lines 137-140, 147-149). Step 5's mutation testing has an unspecified sequencing gap: as written ("after a candidate build passes... flagging surviving mutants to the owner") it reads as a post-hoc audit, and building.py applies a passing candidate to the live project in the same call that verifies it (building.py:690-698, 726-765) with no described gate holding that apply open until mutation testing completes — so a weak check could still ship a bad build before the safety net fires. Step 6's best-of-N voting defends against independent/random model error, not the correlated, systematic error this journey actually documented: the same free model made the same category of mistake (vacuous, wrong-reason, weak-substring) across m4, m5 and two revision rounds (JOURNEY_LOG.md lines 95-133), so several cheap calls from similar weak models are likely to converge on the same flaw rather than disagree about it — "keep agreeing examples" would probably keep exactly the bugs already seen. Several other plausible failure modes the adversary brief asked about have no mechanical safeguard in the text at all: milestones/clauses that are not testable black-box (subjective or architectural), non-CLI target projects, an OS-fragile "read-only folder" fault menu item on the very Windows environment this runs in, non-deterministic generated code (locale/time/random), arithmetic errors baked into the model's own example data, and clause-splitting that silently drops or merges part of a milestone's "done when" text with nothing checking coverage. None of this argues against building the chunked path — it argues for keeping every mechanical safeguard Runesmith already has (required_texts AST scanning, the dry-run trial, declared public interfaces, the one-revision loop) explicitly wired into the new pipeline rather than assuming the redesign makes them redundant, and for closing the "tested against a correct build" and "mutation gates apply" gaps before this path is trusted to run unattended the way G1.1–G1.3 plus the Checker role were needed before the free-form path could be.

- **[must] wrong-reason failure surviving a correct build:** Design step 4 only verifies a check fails TODAY for its stated reason; it never verifies the check would PASS once the milestone is genuinely, correctly built. That is exactly the direction in which m6's real bug lived: it failed today (no README) for a plausible-looking reason, passed the trial and Checker review, then broke the actual chained apply once a correct README existed, because its hard-coded example ran `--file` after the subcommand. → Add a second, symmetric safeguard: before or at approval, run each clause's check against a throwaway reference implementation (owner-supplied when available, otherwise a second small-model 'obviously correct' stub) and require it to pass, mirroring what the chat-window Checker did by hand (JOURNEY_LOG.md:137-140). Do not treat 'fails now, for the stated reason' as sufficient on its own. (D:\oob\JOURNEY_LOG.md:137-140,147-149)
- **[must] mutation testing sequencing:** Step 5 says mutation testing runs 'after a candidate build passes,' but the existing apply path (_apply_if_current) fires in the same call that returns 'acceptance_passed' (building.py:690-698, 726-765), with no described gate holding the apply open until mutants have been tried. A weak check could still let a bad build ship before the mutation safety net runs. → Specify explicitly that mutation testing is a precondition of auto-apply, not a follow-up audit: either run it during the check's dry-run/approval stage against a reference implementation (before any live build), or add an explicit hold in _apply_if_current until a per-check mutation-survival record exists and is clean. (D:\Runesmith\runesmith\app\building.py:690-698,726-765)
- **[must] best-of-N votes on correlated, not random, error:** Step 6 treats agreement among several cheap calls as a signal of correctness, but the documented failures were systematic: the same free model repeated the same category of flaw (vacuous, wrong-reason, weak substring match) across m4, m5, and two separate revision rounds. Several cheap calls sampled from similar weak models are likely to share, not expose, that bias. → State plainly that voting is a secondary/noise filter, not a safety mechanism, and keep the mechanical detectors (required_texts-equivalent scan, dry-run trial, mutation testing) as the load-bearing checks regardless of vote agreement. Do not let 'the models agreed' substitute for a mechanical pass. (D:\oob\JOURNEY_LOG.md:95-133 (m4/m5/m6 across 20:01Z and 20:21Z revision rounds, same free model))
- **[must] weak-assertion regression risk in the trusted templates:** The design assumes trusted templates avoid the substring-match bug that made assertIn('2', stdout) pass because '2026' contains '2', but it never requires the template library itself to be tested against exactly that adversarial case. The only place this is done correctly today is a hand-written checker (word-boundary regex + 'last number on the line') that a strong model wrote by hand, not a codified, regression-tested template. → Require the trusted-template library to ship with its own meta-test suite covering every documented weak-assertion case (substring-in-larger-number, over-permissive 'clear error' on any nonempty stderr, etc.) before templates are marked 'trusted,' and re-run that suite on every template change. (D:\oob\checker\m4.py:8,35-36; D:\oob\JOURNEY_LOG.md:96 ('sentences and the code disagree'))
- **[must] read-only-folder fault menu is OS-fragile on this project's own platform:** The proposed fault MENU includes 'read-only folder,' but this project runs on Windows (win32; building.py already special-cases SYSTEMROOT/WINDIR in its check environment, building.py:87-91), where POSIX-style read-only permissions do not reliably block the owning process from writing. This is precisely the 'flaky/OS-dependent check' category the review was asked to watch for, and it is baked into the design's own fault menu. → Either drop 'read-only folder' from the menu for Windows targets or specify a Windows-correct implementation (e.g., a DENY ACL via icacls, verified in a template meta-test on Windows) before offering it as a trusted, model-selectable fault. (D:\Runesmith\runesmith\app\building.py:87-91; environment banner: Platform win32)
- **[should] no mechanical over-specification detector:** Putting exact literals into owner-reviewed examples (step 2) makes over-specification visible but not caught: nothing mechanically flags a check that requires more than the milestone's done_when text promises, even though it is stated plainly. This reproduces the same failure shape as before G1.3 ('an owner who reads only the sentences would approve both,' JOURNEY_LOG.md:98), just moved from sentences to a table. → Extend the existing required_texts machinery (acceptance_proposals.py:108-134) to also flag literals present in an example/sentence but absent from the milestone's own done_when text, surfacing them as an explicit 'assumption' the owner must accept, the same way G1.1's assumes list works today. (D:\Runesmith\runesmith\app\acceptance_proposals.py:108-134; D:\oob\JOURNEY_LOG.md:98)
- **[should] no determinism/flakiness static check on generated checks:** The TASK prompt asks for 'deterministic data' only as an instruction to the model (acceptance_proposals.py:42-43); nothing in validate() or the new design statically scans generated example/template code for datetime.now(), unseeded randomness, sleeps, or locale-dependent formatting, so a flaky check can still be approved. → Add an AST-level scan (alongside required_texts) over generated code for known non-determinism sources and reject or flag them before the owner sees the proposal. (D:\Runesmith\runesmith\app\acceptance_proposals.py:40-54,137-188)
- **[should] no validation that the model's own example data is internally correct:** A model can propose setup data plus an expected outcome that is arithmetically or logically wrong for that setup (e.g. a miscounted total). Steps 2-5 test whether the check fails now for the stated reason and survives mutation, but nothing independently re-derives the expected value from the stated setup, so a wrong check could reject correct builds and burn ordinary_allowance attempts before surfacing to the owner. → For mechanically-checkable outcome types (counts, sort order, presence/absence), have Runesmith itself recompute the expected value from the stated setup with a small trusted calculator and require it to match the model's claimed outcome before the example is accepted. (D:\Runesmith\runesmith\app\building.py:382-397 (ordinary_allowance budget consumed by repeated failing attempts))
- **[should] no path for a clause that is not testable black-box:** Chunking by clause (step 1) reduces the size of an untestable requirement without resolving its untestability — a subjective or architectural clause ('the message is friendly', 'the code is maintainable') chunked smaller is still not mechanically checkable, and nothing routes it away from being forced into a template, which risks manufacturing a vacuous-by-construction check. → Add an explicit per-clause testability classification step: a clause that cannot be reduced to an observable, black-box outcome is routed to owner sign-off instead of a generated check, rather than silently forcing a template onto it. (Adversary instruction category: 'a milestone that is not testable black-box')
- **[should] clause-splitting coverage is unguarded:** Step 1 does not specify whether splitting the milestone's done_when into clauses is mechanical or model-driven, or how Runesmith verifies the union of generated clause-checks still covers the full done_when text. A dropped or silently merged clause (e.g. an interaction between two stated behaviours) narrows coverage with nothing to detect it, unlike the mechanical unstated-text detector that exists for the current single-shot path. → Require an explicit coverage check comparing the milestone's done_when text against the union of clause sentences (a required_texts-style diff in the other direction), flagging any clause of the original text that no generated check maps to. (D:\Runesmith\runesmith\app\acceptance_proposals.py:108-134 (existing detector runs the opposite direction: code vs sentence, not milestone vs clauses))

### feasibility

The design maps onto the existing code cleanly for its data/execution core, less cleanly for its two most ambitious pieces. acceptance_proposals.py was already architected as a narrow, swappable front end (whatever produces {checks, assumes, code}) feeding a fixed, well-tested back end (validate, dry_run, findings, approve/discard, FOOTER's PUBLIC_CRITERIA mapping, the RUNNER subprocess template, _run_checks). Examples-as-data plus trusted templates is exactly that kind of front end: a propose_examples() that renders reviewed example rows into the same shape can reuse essentially the whole existing pipeline unchanged, and can even structurally prevent the sentence/code-contradiction and hidden-exact-text flaw classes rather than detect them after the fact. Chunking by clause and best-of-N need no new product-level wiring (the existing 'acceptance' role and its repeat-call pattern from _revise_once already support it) but multiply model calls in a way the journey's own observed latencies (5-15s good case, 211s timeout case) say must be bounded. Mutation testing is the one genuinely new capability: it can be placed correctly -- inside verify_draft, right after the owner-acceptance check succeeds and before record()/apply, mutating candidate bytes in Runesmith's own process and running each mutant through the unchanged _run_checks on a fresh clean stage -- which satisfies both stated invariants (runners never import runesmith; checks run on a clean copy) by construction, but it is new engineering (an AST mutator library) with real added latency and an unresolved product question (gate apply on surviving mutants, or just warn). The smallest slice that is genuinely small and immediately measurable against the live m4-m6 record is templates + examples at today's one-call-per-milestone granularity, deferring clause-splitting, voting, and mutation testing to later slices once that core swap is proven.

- **[must] Back-end reuse: examples can terminate in today's proposal shape:** It looks like the chunked/examples design (points 1-4) requires new persistence, validation, execution and approval machinery. → It doesn't. acceptance_proposals.py already separates a swappable front end (whatever produces {checks, assumes, code}) from a fixed back end. validate() (L137-188), dry_run() (L301-329), findings() (L266-274), approve()/discard() (L358-405), FOOTER (L333-339), public_criteria() (L342-355), the RUNNER template and _run_checks() (building.py L30-71, L83-118) all operate on that shape regardless of how it was produced. A new propose_examples() only needs to render examples into the same {checks, assumes, code} dict and hand it to the existing pipeline. Recommend extracting propose()'s persistence tail (validate -> dry_run -> findings/revise -> persist -> ledger, L250-263) into a small shared helper so both the freeform and example paths call it, instead of duplicating it.
- **[should] Chunking and best-of-N need no new product wiring:** Design points 1 and 6 (per-clause calls, several votes per clause) look like they need new roles in Thinking power, following the precedent of the Checker role added mid-journey. → They don't. workspace.py's ROLES tuple already has a single 'acceptance' role (L44-47) that falls back to the Planner's instrument list (L409-410), and _revise_once() (acceptance_proposals.py L277-298) already shows the pattern of a second call on the same role with a distinct key. Per-clause and per-vote calls are just router.call('acceptance', ..., key=...) repeated with different keys -- no new role, no new 'Who does what' entry needed for v0. The real cost is call count (clauses x votes), not new wiring; that needs a bound (see next finding).
- **[should] Call-count multiplication vs. observed live latencies:** Chunking by clause and best-of-N multiply model calls per milestone (e.g. 4 clauses x 3 votes = 12 calls for one milestone), against a background where the journey already saw calls take 5-15s on the free route and time out at 211s on a stronger free route (JOURNEY_LOG.md L104, L130). → Cap total calls per milestone (mirroring SCHEMA's existing maxItems:8 check cap, acceptance_proposals.py L31) and treat a single clause-call failure/timeout the same way today's single acceptance call failure is handled (PlannerUnavailable, L243-245), not as a reason to retry silently across all clauses.
- **[must] "Fails for the stated reason" needs a small dry_run() extension:** Design point 4 wants each example's stated failure reason checked against the actual failure on today's code, but dry_run() (acceptance_proposals.py L301-329) discards the per-test failure detail. → _run_checks() (building.py L83-118, via the RUNNER at L64-70) already computes failure_details (test id + trace_tail) but dry_run() only keeps aggregate ran/failures/errors counts. Add 'failure_details': result.get('failure_details', []) to dry_run()'s return, and a small comparator (e.g. substring/keyword match against trace_tail) that flags a mismatch the same way findings() already flags passes_now/broken (L266-274). This is a small, low-risk, concretely scoped change.
- **[should] Owner UI: example table is additive, not a rewrite:** It's unclear whether the owner UI for a table of examples needs new endpoints or a new approval flow. → No. goals.js's accBlock (L226-291) already renders a proposal generically from p.checks/p.assumes and wires Approve/Discard/Replace to milestone-and-proposal-id-only endpoints (server.py L461-475) that don't care about provenance. An example table is an additive rendering branch (columns: clause, setup, command, expected outcome/matcher, why it fails today, fault) keyed on a new field, reusing the same approve/discard calls untouched. This is real but bounded new JS work (~80-150 lines), not new backend surface.
- **[should] Mutation testing hook point and rule compliance:** Need to place mutation testing 'after checks pass, before apply' without check runners importing runesmith and without checks running on anything but a clean copy. → Hook it inside verify_draft() (building.py L186-292) right after oracle = _run_checks(...) succeeds (~L281) and before record()/return (L288-292). Mutate the *bytes* of frozen_files in Runesmith's own process (an AST-based mutator, in the same spirit as the already-established AST helpers _literals/required_texts, acceptance_proposals.py L93-134, and _candidate_files' encode_like, building.py L121-134) -- never inside the subprocess. Write each mutant to its own fresh tempfile.TemporaryDirectory (mirroring the acceptance-stage pattern at L277-278) and run it through the unchanged _run_checks(..., json.dumps(frozen_paths), ...) call. Because the RUNNER template (L30-71) and the subprocess entry point never change, and each mutant gets a brand-new clean stage exactly like today's acceptance phase, both stated rules hold by construction. For v0, make the result advisory (a non-blocking 'weak spot' callout next to the checks) rather than gating _apply_if_current -- mirrors the existing non-blocking passes_now trial warning (FINDINGS L59-60, goals.js L249-253) -- since the design doc doesn't settle what should happen to a milestone whose checks have surviving mutants.
- **[should] Mutation testing cost and caching:** Each mutant needs a full _run_checks() subprocess call bounded by CHECK_TIMEOUT_S=120s (building.py L28, L84-85); running several mutants per milestone on every scheduled round would meaningfully slow or repeatedly re-pay for unattended building. → Cap mutant count small (comparable to the 8-check cap already used elsewhere) and cache/skip mutation testing when nothing changed, reusing the same digest-based skip logic _unchanged_verdict() already applies to full rechecks (building.py L305-326, keyed on snapshot_digest and acceptance_bundle hashes).
- **[should] Fault MENU: "read-only folder" is platform-fragile on Windows:** This product runs on Windows (D:\Runesmith). A naive 'make the folder read-only' fault (os.chmod/Path.chmod) does not reliably block the owning process from writing, unlike POSIX permission bits -- so it would likely fail to simulate the intended failure, unlike the interrupted-write fault, which is a monkeypatch on io.open/builtins.open (D:\oob\checker\m5.py L9-43) already hand-validated live against real and reference code (JOURNEY_LOG.md L137-141). → Limit the v0 fault MENU to faults already validated live in the journey -- interrupted write (open() patch), damaged file (corrupt bytes), missing file (delete it) -- and treat 'read-only folder' as a later Windows-specific item (e.g. via icacls), not a v0 fault.
- **[should] Clause splitting reintroduces the weak-model risk one layer up, unguarded:** Design point 1's 'one small model call per clause' asks a model to read done_when and split it, but this new step has none of the mechanical safeguards (required_texts, dry_run's trial, revise-once) that acceptance_proposals.py built specifically because a free model's *checks* proved unreliable (JOURNEY_LOG.md L95-133) -- a mis-split or hallucinated clause is plain text, not code, so it can't be statically checked the same way. → For v0, split done_when deterministically (sentence/semicolon/'’and’' segmentation of the field already fetched by _milestone(), acceptance_proposals.py L81-85, L194) instead of a model call. Defer a model-driven adaptive split to a later slice, once the template system itself is proven on today's granularity.
- **[must] Smallest measurable first slice:** The task asks for the smallest slice buildable and measurable on m4-m6, with size and risk. → Build only: (a) acceptance_templates.py, a small trusted-template library covering the three matcher shapes already hand-validated live -- tolerant line match (D:\oob\checker\m4.py's MONTH regex approach), no-Traceback/damaged-file check and interrupted-write fault (m5.py), README-example extraction-and-run (m6.py) -- roughly 300-400 lines, largely adapting the already-proven 52-82 line files directly; (b) acceptance_examples.py, a schema + validate_examples() + propose_examples() that renders one example per milestone (today's granularity, no clause split, no vote) into the existing {checks, assumes, code} shape and hands it to the unchanged validate()/dry_run()/approve() pipeline, roughly 150-250 lines; (c) a small refactor of acceptance_proposals.propose() to share its persistence tail; (d) worker.py/server.py wiring mirroring the existing propose_acceptance job (worker.py L333, L506, L649-657; server.py L327), roughly 15-25 lines; (e) a goals.js table-rendering branch, roughly 80-150 lines. Total order of magnitude: 600-900 new/changed lines, comparable to one of the G1.x fixes already shipped in a single evening per the journey log. Measure by rerunning the exact R1 Phase B recipe (JOURNEY_LOG.md L87-171) with the same free model (Gemini 3.1 Flash Lite) through propose_examples() instead of propose(), and counting how many of the 7 documented flaws recur and whether the Checker-role chat-relay rescue (L136-141) is still needed. Leave mutation testing and clause-splitting/best-of-N for later slices, since they are the least proven and highest-latency-risk pieces.
- **[could] Structural fix available: derive sentences from the same data as the code:** Three of the seven documented flaws (hidden exact text, sentence/code contradiction, weak assertions) come from a model writing both the code and its plain-English description separately, so they can drift apart. → Because templates render both the assertion and can own a matching sentence template (e.g. 'the report line for {month} shows {count}' generated from the same {month, count} row the matcher uses), the example-based path can make this class of bug structurally impossible rather than merely detected after the fact the way required_texts()/G1.3 does today (acceptance_proposals.py L108-134, L166, L177-178). Keep required_texts() running anyway as cheap defense-in-depth against a template-rendering bug that leaks an extra literal, rather than removing it.

### generality

Grounded in the actual code (acceptance_proposals.py, building.py, acceptance_contracts.py) and the real Phase B checker files (m4/m5/m6.py) plus the journey log, the chunking/example-template idea is a sound extension of a pattern the codebase already proves works: generate cheaply, then let a mechanical harness cross-check what the model claims against what its own artifact actually requires (required_texts(), dry_run(), the one-revision loop), rather than trusting a weak model's self-report. The real m4-m6 checks show a small library of primitives (subprocess+tolerant-regex extraction, one open()-patching fault harness, byte-comparison of damaged files, README-example extraction with placeholder filtering) already covers one CLI/file-based project completely, which is good evidence "trusted templates" are feasible for that category. But the design as stated has real gaps once checked against the code: two of its own listed fault-menu items (slow/failing network, and by extension any web/HTTP service testing) directly collide with the NETWORK_MODULES safety gate that validate() already enforces and the design never reconciles that; "fails for the stated reason" — the single mechanism that would actually fix the recurring wrong-reason-failure bug that motivated this whole proposal — has no concrete verification method proposed beyond the name, even though the pieces to build one (RUNNER's failure_details/trace_tail) already exist unused; "read-only folder" as stated would likely not even fault on the Windows platform this runs on; and best-of-N voting, while mechanically cheap to implement (structured-data comparison instead of code-semantics judgment), is not budgeted against the free-tier capacity limits (F12, 211s timeouts, capacity refusals) that this exact journey already hit at a much lower call volume. None of these are fatal to the idea, but each needs a concrete decision before "chunk the checks too" is actually safe to build, not just plausible.

- **[must] Network faults collide with the existing no-network gate:** The proposed fault menu includes "slow/failing network," but acceptance_proposals.validate() statically rejects any check file that imports socket, ssl, urllib, http, requests, ftplib, smtplib, telnetlib or asyncio (NETWORK_MODULES, lines 61 and 154-155), and this is deliberate: checks must be offline and deterministic. A template that simulates a slow/failing network (even purely to fail the *project's* outbound call locally, never touching the real network) would need one of those modules to intercept it, and would be rejected by the same AST scan that today catches the good case (a check that snuck in real network use). The design doc doesn't mention this collision at all. → Decide explicitly: either (a) scope this fault out of the menu until there's a real HTTP/network-service use case, or (b) carve out a narrow exception where only Runesmith's own trusted-template code (never model-authored code) may use these modules, and statically verify the inserted snippet never opens a real socket (e.g. only patches; always loopback-bound or in-process). Do not let a model-chosen menu item silently need a change to validate()'s safety gate.
- **[must] "Fails for the stated reason" has no generic verification mechanism yet:** This is the core motivation for the whole proposal (it names the exact m6 bug twice: JOURNEY_LOG.md lines 128 and 148, where checks failed today for a reason no README could fix). But today's dry_run() (acceptance_proposals.py 301-329) and findings() (266-274) only look at the coarse verdict — FINDINGS only has 'passes_now' and 'broken' keys (line 59-60); there is no check of *why* it failed. Meanwhile building.py's RUNNER already captures per-failure trace_tail and criteria in failure_details (lines 66-70), unused for this purpose. Without a mechanism to compare the actual failure against the stated reason, "fails for the stated reason" is just a restatement of the goal, not a design. → Give each example a machine-checkable failure signature (a substring/regex expected in the failure's trace_tail or stdout/stderr, already captured by RUNNER) and have the trial check it, reusing the existing revise-once flow (_revise_once) when it doesn't match. For fault-menu-based examples specifically, go further: since Runesmith's own template injects the fault (as m5.py's open()-patching already does), have the template record a sentinel when *its own* injected exception is the one that propagated, rather than re-deriving "why" by scraping output after the fact — this is deterministic and doesn't depend on the project's exact wording.
- **[should] "Read-only folder" fault is not portable to the platform this actually runs on:** This environment is win32, and building.py's _run_checks() already treats Windows specially in its stripped subprocess env (SYSTEMROOT/COMSPEC among the allowed keys, lines 87-91), but nowhere in building.py or acceptance_proposals.py is there any chmod/ACL handling. On Windows, os.chmod-based read-only enforcement doesn't reliably block writes the way it does on POSIX (it only sets FILE_ATTRIBUTE_READONLY, which behaves differently for files vs. directories and is trivially bypassable). Treating "read-only folder" as a real-filesystem-permission fault will likely produce a fault that doesn't actually fault on Windows. → Implement "read-only folder" the same way m5.py already implements "interrupted write": patch io.open/builtins.open (or os.makedirs/os.remove as needed) to unconditionally raise PermissionError for paths under the given folder, rather than relying on real OS permissions. This also unifies three of the five fault-menu items (interrupted write, damaged file via a preset corrupt fixture, read-only folder) into one open()-patching trusted template with different parameters, rather than three separate template implementations.
- **[should] Best-of-N cost isn't budgeted against the free route's known capacity limits:** Today's propose() makes at most 2 model calls per milestone (one draft, one revision — acceptance_proposals.py 226-263). This exact journey already hit real capacity limits at that volume: 'nvidia capacity reached; no alternative route available' on every acceptance call (JOURNEY_LOG.md line 90), a 211s-per-call, 10.5-minute-total timeout when Kimi K3 was tried (lines 129-132), and F12, an unfixed router gap where a pre-admission refusal doesn't fall through to the next route. Chunking a milestone into several clauses and voting N times per clause (design step 6) multiplies call count 5-10x on the same free/rate-limited routes. → State an explicit budget and degrade-gracefully rule: e.g., accept a vote once >=2 of N calls succeed and agree, cap total calls per milestone, and fall back to a single un-voted call per clause (or the existing whole-milestone free-form path) if the route is refusing or timing out, rather than multiplying exposure to the exact F12/timeout failure modes already logged.
- **[should] Web/HTTP services need a scope decision, not just "another template family":** Testing an HTTP service from the outside needs the acceptance file to make HTTP calls, which collides with the same NETWORK_MODULES gate as the network fault (validate(), lines 61/154-155). This is a different kind of decision than adding a new tolerant matcher — it's the same category of trust/scope call the journey log already treats deliberately (the temporary Milliner gate, 'free routes only, no paid/metered fallback', stripped env). Lumping it in with 'file outputs' or 'data pipelines' as just another supported category understates the work. → Treat web/HTTP services as either out of scope for v1 (free-form fallback only, and even then only if a loopback exception to the network ban is granted) or as a named, separately-reviewed scope decision with its own narrow loopback-only carve-out — analogous to how the temporary gate was scoped and is meant to be removed after release.
- **[could] Clause chunking should reuse the existing generate-then-cross-check pattern, not rely on trusting the split:** done_when is stored as free text (planner.py line 38, no enforced list structure), so a weak model's clause boundaries can't be assumed reliable. The journey log's core lesson (repeated across G1.1-G1.3) is that a rule stated in the prompt is not enough on its own — the harness has to check it mechanically (e.g. required_texts(), acceptance_proposals.py 108-134, which AST-scans a model's own code for exact literals the model's sentence didn't mention). Clause splitting is lower-risk than check-authoring (it's extraction, not code-writing) but the design doesn't say how a bad split (missed clause, invented clause, merged clauses) would be caught. → Apply the same discipline already proven in required_texts(): after the model splits done_when into clauses, mechanically check that the union of clauses accounts for every quoted literal/number/named entity in the original text (flag leftover, uncovered text to the owner, don't silently drop it), and reserve best-of-N specifically for this cheap step (clause splitting) rather than only at the full-example stage, since disagreement here is cheap to detect via plain string/set comparison.
- **[could] CLI vs. import/call vs. GUI templates need to be named as distinct coverage tiers, not one bucket:** The real m4/m5/m6 checks (checker/m4.py, m5.py, m6.py) are entirely subprocess+stdout/file based, which the TASK prompt already prefers (acceptance_proposals.py lines 40-41) and which is language-agnostic on the target side (subprocess works against any language's CLI). But an 'import the function and check its return value' template is Python-only, and GUI milestones have no black-box automation surface anywhere in this codebase (_run_checks strips the env and runs headless unittest, building.py 83-118) — there's no accessibility-tree or screenshot layer to build a template on. The reviewer question lists these as one flat list of categories to sort into 'template' or 'fallback', which risks implying they're equally close to done. → Rank coverage explicitly: (1) CLI/subprocess-based projects, any target language — proven today, template-ready; (2) Python library import/call — template-ready but a distinct, Python-only template family; (3) file-output and simple numeric-tolerance data pipelines — template-ready with a new tolerant-matcher type; (4) README/doc examples — mostly template-ready (m6 proves it) but blocked by project-specific CLI-grammar quirks (the exact --file-placement bug that shipped, JOURNEY_LOG.md line 128) unless the template first learns the real grammar from --help output; (5) web/HTTP services and GUIs — not template-ready, need new infrastructure/scope decisions, free-form (or nothing) for now.
